# ArbiQuest 8.91 — одноразове налаштування захищеної адмінпанелі

Клієнт уже містить панель, але нові серверні операції навмисно недоступні до налаштування. Публікація GitHub Pages НЕ публікує правила Firebase.

1. Firebase Console → Authentication → Users: знайдіть СПРАВЖНІЙ акаунт власника Sw1nther/swinther і скопіюйте його UID. Нік не є доказом особи. Не обирайте тестувальника, ArbiQuestMetod чи інший акаунт з роллю dev/owner.
2. Firestore Database → Rules: замініть правила ВМІСТОМ `firestore.rules` з цього репозиторію та натисніть **Publish**. Зберігати старі широкі allow-правила поряд із новими не можна: allow об’єднуються через OR.
3. Firestore Database → Data: через Console створіть документ `adminIdentity/owner`:
   - `uid` (string): UID справжнього власника з кроку1;
   - `rulesVersion` (string): `8.91`.
   Необов’язково: `email` (string) — точна підтверджена пошта власника. Якщо поле додано, вхід має бути з цією поштою та email_verified=true. Жодних паролів/токенів у документі!
4. Перезавантажте сайт, увійдіть онлайн як власник. З’явиться Dev-панель; зелений статус означає, що ідентичність підтверджена сервером. Першу тестову дію виконайте для свого тестового акаунта, не для друга, перевірте журнал і отримання зміни на другому пристрої.

`adminIdentity/owner` змінюється ТІЛЬКИ через Firebase Console / довірений Admin SDK. Клієнтам заборонено змінювати ідентичність, журнал чи надавати роль owner. Старі roles, local dev flags і ніки не дають адміндоступу. До налаштування онлайн адмінпанель прихована для всіх, керування вимкнене; звичайне навчання продовжує працювати зі старими правилами.

Схема:
- `moderation/{uid}`: публічні blocked/tester/nick + actionId, без причин і пошти. Запис — лише власник, атомарно з відповідним записом журналу.
- `siteConfig/global`: оголошення, перемикачі, перерва, XP-подія; запис лише власником та атомарно з журналом.
- `adminActions/{id}`: незмінний журнал і команда доставки. Створює лише власник; редагування/видалення заборонене навіть власнику. Користувач читає лише власні команди, власник — усі. Причини блокування не публікуються у спільноті.

Блокування та maintenance перевіряються Firestore на записах users/publicProfiles/gifts незалежно від UI. Вимкнення community блокує публікацію рейтингу й подарунків, але не приватне збереження уроків. Виділеної колекції чатів/коментарів зараз немає: невідомі колекції залишаються default-deny. Якщо додати їх пізніше — потрібні окремі правила з перевіркою blocked/maintenance.

Зміни XP/монет/предметів/ачівок/прогресу доставляються як команди: застосуються при підключенні користувача; повторна доставка не повторює нагороду. Це не Cloud Function і не синхронна перезаписана сесія іншого користувача. Локальне офлайн-навчання не можна дистанційно відкликати без інтернету, але сервер не прийме записи заблокованого акаунта. XP-множник і shop toggle — механіки клієнта, а не повноцінна серверна античит-економіка: існуючий прогрес зберігається JSON-рядком. Перевірка owner-only записів команд і модерації при цьому серверна.

Важливо: правила підготовлено; реальний deploy і перевірка production Firebase з обліковими даними власника агентом не виконувалися. Локальні тестові сценарії — у /workspace/qa/admin97-test.cjs; Firestore emulator потрібен для окремої серверної валідації перед production Publish.

Локальна перевірка правил: підготовлено `/workspace/qa/firetest/rules-test.cjs` і конфіг emulator. Запуск після встановлення Java: `cd /workspace/qa/firetest && ./node_modules/.bin/firebase emulators:exec --project demo-aq-admin97 --only firestore "node rules-test.cjs"`. На цій машині Java відсутня; встановлення через apt не вдалося (помилка репозиторію), тому ці серверні тести НЕ запускались. Перевірки UI/команд виконані з mock Firestore.
